Set up in 3 minutes

  1. Unzip. Open TriageLab.xcodeproj in Xcode 16 or newer.
  2. Pick an iPhone Simulator. Press ⌘R. Tap a case.
  3. For the cases marked real phone (C02, C14, C31, C32, C30) use an iPhone. Set your Team in Signing.
  4. Do not read the Swift files first. Read the report, trigger the bug, then investigate. Hints are in the app and here.
  5. If a build error appears, open an issue with the error text. Parts of this project were written without running Xcode.

Logic/L01_VitalsMonitor.swiftCaseViews/W1_Memory.swift

Stuck? Open one hint at a time

Hint 1

Use the Memory gauge, then press the Debug Memory Graph button (three connected circles) in the debug bar.

Hint 2

In the memory graph filter for VitalsMonitor. Count them. In the Console search the log for 'VitalsMonitor'.

Hint 3

Something keeps each monitor alive after you leave the screen. Look at the timer and what its closure captures.

Show the answer (try first!)
Root cause
  • A repeating Timer keeps its closure. The closure captures self strongly. The timer is never stopped.
  • The run loop holds the timer. The timer holds the closure. The closure holds the monitor. So the monitor never leaves memory.
How to PROVE it (what you should see)
  • Black Box > Live objects: VitalsMonitor: 5 alive after 5 visits. It should be 0 or 1.
  • Console: filter VitalsMonitor. You see 5 init lines and 0 deinit lines.
  • Debug Memory Graph: 5 VitalsMonitor objects. Click one. The arrows lead to a Timer and a closure.
  • Memory gauge grows about 400 KB per second for every leaked monitor.
Fix
timer = Timer.scheduledTimer(withTimeInterval: 0.5, repeats: true) { [weak self] _ in
    guard let self else { return }
    self.chartBuffers.append(Data(repeating: 1, count: 200_000))
    self.onTick?()
}

func stop() {
    timer?.invalidate()
    timer = nil
}
// call monitor.stop() from .onDisappear
Prevent it next time
  • Log deinit for long-lived objects.
  • Stop timers and tasks when the screen goes away.
  • Run the Leaks instrument before release.
One-line summary

I filtered the memory graph for the type, saw 5 leaked instances, and followed the arrows to a timer closure that captured self strongly.

Logic/L02_PhotoLoader.swiftCaseViews/W1_Memory.swift

Stuck? Open one hint at a time

Hint 1

There is no crash report. Think: who else can close an app? Check the Black Box screen after the app closes.

Hint 2

Look at how many photos are held in memory at once and how big each one is (4032 x 3024 pixels, 4 bytes per pixel).

Hint 3

Every photo is decoded at full size and all are kept in an array. 24 photos is more than 1 GB.

Show the answer (try first!)
Root cause
  • Each photo is decoded at full size: 4032 x 3024 x 4 bytes is about 48.8 MB.
  • All photos are kept at once. 24 photos is about 1.1 GB. iOS closes the app when it passes its memory limit. No crash report is made.
How to PROVE it (what you should see)
  • Memory gauge jumps by about 49 MB per photo.
  • Instruments > Allocations: big [UInt8] buffers. VM Tracker shows dirty memory growing.

Fix
// Do not decode full size. Make a small thumbnail with ImageIO.
let options: [CFString: Any] = [
    kCGImageSourceCreateThumbnailFromImageAlways: true,
    kCGImageSourceThumbnailMaxPixelSize: 600,
    kCGImageSourceCreateThumbnailWithTransform: true
]
let thumbnail = CGImageSourceCreateThumbnailAtIndex(source, 0, options as CFDictionary)
// Keep only the visible photos. Load 2 or 3 at a time.
Prevent it next time
  • Check memory left before heavy work.
  • Test with 50 photos on the oldest phone.
  • Alert on unknown_in_foreground per app version.
One-line summary

No crash report means iOS closed it. I read the last-run log, did the memory math (48 MB per decoded photo), and fixed it by downsampling.

Logic/L09_ReadingBuffer.swift

Stuck? Open one hint at a time

Hint 1

Turn on Thread Sanitizer and run again.

Hint 2

How many threads add to the same array?

Hint 3

An array is not safe for many writers.

Show the answer (try first!)
Root cause
  • concurrentPerform runs many threads. They all call values.append on one array without a lock. This is a data race.
How to PROVE it (what you should see)
  • Thread Sanitizer: Data race detected (Issue Navigator). Two threads write the same address. It reports this on every run.
  • Without the Sanitizer the count may look right on some runs. On a Mac with many cores it is often lower, and sometimes the app crashes. A race does not fail every time. That is why it is dangerous.
Fix
final class ReadingBuffer {
    private let queue = DispatchQueue(label: "readings")
    private var values: [Int] = []

    func add(_ value: Int) {
        queue.sync {
            values.append(value)
        }
    }

    var count: Int {
        queue.sync {
            values.count
        }
    }
}
Prevent it next time
  • One owner for shared data: a lock, a serial queue, or an actor.
  • Run Thread Sanitizer in CI.
One-line summary

Random wrong counts and malloc crashes mean a data race. Thread Sanitizer pointed at the array. I gave the data one owner.

    }

        DispatchQueue.main.async {
            completion(text)
        }
    }
}
// The caller shows a spinner and updates when the completion runs.

  • Main Thread Checker and a hang detector in debug.

Show the answer (try first!)

  • Nothing stops it when you leave the screen.

Fix
func start() {
    // 10 times a second is enough, and batch the writes.
    timer = Timer.scheduledTimer(withTimeInterval: 0.1, repeats: true) { [weak self] _ in
        self?.collect()
    }
}

func stop() {
    timer?.invalidate()
    timer = nil
    flushBufferToDisk()
}
// Write in batches. Call stop() when the feature is not needed.

  • Lowest rate that works.
  • Batch disk writes.
  • Stop work when the screen is gone.
