# C01: Memory climbs on the vitals screen

**Family:** Ward 1: Memory and silent kills  
**Severity:** High

## Field report

> Nurses say the app gets slower and warmer each time they check vitals. Memory keeps climbing.

## 1. Reproduce

Open the Vitals monitor, go back. Repeat 5 times.Watch the memory number on the screen and in Xcode (Debug Navigator, Memory).No heap tool? Open Black Box > Live objects. Count VitalsMonitor.

## 2. Tools to try

- Xcode Memory gauge
- Debug Memory Graph button
- Instruments: Allocations or Leaks
- Black Box > Live objects (works without any tool)
- Console log (init / deinit lines)

## Answer

<details><summary>Show the answer (try first!)</summary>

### Root cause

- A repeating Timer keeps its closure. The closure captures `self` strongly. The timer is never stopped.
- The run loop holds the timer. The timer holds the closure. The closure holds the monitor. So the monitor never leaves memory.

### How to prove it

- Black Box > Live objects: `VitalsMonitor: 5 alive` after 5 visits. It should be 0 or 1.
- Console: filter `VitalsMonitor`. You see 5 `init` lines and 0 `deinit` lines.
- Debug Memory Graph: 5 VitalsMonitor objects. Click one. The arrows lead to a Timer and a closure.
- Memory gauge grows about 400 KB per second for every leaked monitor.

### Fix

```swift
timer = Timer.scheduledTimer(withTimeInterval: 0.5, repeats: true) { [weak self] _ in
    guard let self else { return }
    self.chartBuffers.append(Data(repeating: 1, count: 200_000))
    self.onTick?()
}

func stop() {
    timer?.invalidate()
    timer = nil
}
// call monitor.stop() from .onDisappear
```

### Prevent it next time

- Log `deinit` for long-lived objects.
- Stop timers and tasks when the screen goes away.
- Run the Leaks instrument before release.

### One-line summary

I filtered the memory graph for the type, saw 5 leaked instances, and followed the arrows to a timer closure that captured self strongly.

</details>
